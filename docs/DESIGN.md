# On-Connect 設計企画書

**幼稚園・保育園・学校向け 職員間コミュニケーションアプリ**

作成日：2026年7月31日（開発理念・音声通話・予算感・ブランドデザイン・権限管理 反映版）
開発：Onga-Mirai-Tech

---

## 1. 開発理念・コンセプト

### 1.1 課題認識
- Slack、Microsoft Teamsなどの既存の大規模チーム向けサービスは、多機能・高拡張性である反面、幼稚園・保育園・学校のような小〜中規模組織にとっては機能過多で、導入・運用の負担が大きい。
- LINE WORKS、ChatWorkなどの小〜中チーム向けサービスは、導入負担は小さいものの、現場特有のニーズ（緊急連絡の扱い、予約送信、閲覧限定のカレンダー連携など）に「痒いところに手が届かない」場面がある。
- 幼稚園・保育園・学校では組織支給の端末を用意できないケースが多く、職員自身のスマートフォンが業務連絡のメイン端末となりがちである。
- その結果、私用端末と業務連絡が一体化し、**「つながらない権利」（勤務時間外・休暇中に業務連絡から離れる権利）の確保が構造的に難しい**という課題がある。

### 1.2 開発理念
On-Connectは、大規模チーム向けサービスの「過剰さ」と、小〜中チーム向けサービスの「物足りなさ」の中間を狙い、幼稚園・保育園・学校という現場に特化した機能に絞り込む。特に、私用端末利用が前提となる環境だからこそ、**通知のON/OFFという「つながり方の主導権を職員自身が持てる」仕組み**を中核の設計思想に据える。また、Googleフォームのように既に確立された無料サービスで代替可能な機能は自前で作り込まず、外部サイトへのリンクとして案内することで、開発・運用コストを現場規模に見合った範囲に抑える方針とする。

### 1.3 アプリ名に込めた想い
「**On-Connect**」という名称は、"Connect"（つながり）の"On/Off"を切り替えられることを強調したネーミングである。業務上必要なつながりは確保しつつ、職員自身の意思で「つながらない時間」を持てることを、アプリ名そのものに表現している。

### 1.4 開発体制
- 開発者名義：**Onga-Mirai-Tech**

## 4. システム全体構成（アーキテクチャ）

### 4.1 全体方針
運用コストと保守性を重視し、**サーバーレス構成**を基本とする。モバイルはクロスプラットフォームフレームワーク、Webは同一のバックエンドAPIを共有する構成とする。

### 4.2 構成要素

**フロントエンド**
- モバイル（iOS/Android）：React Native
- Web（Chrome）：React（SPA）

**バックエンド（AWS）**

| 機能 | 使用サービス | 役割 |
|---|---|---|
| ユーザー認証 | Amazon Cognito | ログイン管理、ロール別権限制御（Cognitoグループ） |
| API | Amazon API Gateway + AWS Lambda | REST/GraphQL API、業務ロジック |
| リアルタイムチャット | AWS AppSync（GraphQL Subscriptions） | チャットのリアルタイム配信 |
| 予約送信 | Amazon EventBridge Scheduler + AWS Lambda | 指定時刻でのメッセージ自動送信 |
| **音声通話** | **Amazon Chime SDK** | **1対1音声通話（WebRTCベース、TURN/STUNはSDKが管理）** |
| データベース | Amazon DynamoDB | ユーザー・チャット・掲示板・通話ログ等 |
| ファイル保存 | Amazon S3 | チャット・掲示板の添付ファイル |
| 配信高速化 | Amazon CloudFront | 静的コンテンツ・添付ファイル配信 |
| プッシュ通知 | Amazon Pinpoint / Amazon SNS | 新着チャット・掲示板・着信通知、通知ON/OFF・緊急通知の制御 |
| 外部連携 | AWS Lambda + Google Calendar API | カレンダー情報の取得・キャッシュ |
| ログ・監視 | Amazon CloudWatch、AWS CloudTrail | 稼働監視、監査ログ |
| セキュリティ | AWS WAF（任意）、AWS KMS、IAM | 通信保護、データ暗号化、権限管理 |
| インフラ管理 | AWS CDK もしくは CloudFormation | Infrastructure as Codeによる構成管理 |

## 5. 機能要件詳細

### 5.1 ユーザー管理

#### 5.1.1 ログイン管理
- Amazon Cognito ユーザープールによる認証（メールアドレス＋パスワード、必要に応じてMFA）
- トークンの有効期限・リフレッシュトークンによるセッション管理

#### 5.1.2 ステータス管理（通知オン／オフ）
- 各ユーザーは自身のステータスを「通知オン」「通知オフ」で切り替え可能（個人設定画面）
- **通知オフ時の挙動**
  - プッシュ通知（新規チャット・新規掲示板・**音声通話の着信含む**）は一切配信されない
  - ただし、アプリを開けば新規チャット・新規掲示板の内容は通常どおり閲覧可能（未読バッジ表示等は妨げない）
  - チャットの「緊急通知」フラグ付きメッセージのみ通知オフでも配信される例外を設けるが、**音声通話の着信はこの例外の対象外とし、通知オフ中は一切鳴動しない**（「つながらない権利」を明確に担保するための仕様）
- **実装方針**：`Users` テーブルに `notificationStatus`（ON/OFF）を保持し、プッシュ通知送信用Lambda内で送信可否を判定する。

#### 5.1.3 ロール管理（権限のカスタマイズ）
- 初期ロール例：**管理者**（園長・主任等）／**一般職員**
- 各ロールが持つ権限項目（ユーザー管理、緊急通知の送信可否、掲示板カテゴリー管理、リンク集管理 等）は固定せず、**管理者画面上でロールごとにON/OFF編集できる**仕様とする
- ロールの新規作成・削除にも対応し、組織構成の変化に応じて権限セットを柔軟に調整可能とする
- **実装方針**：Cognitoグループでユーザーの大まかな括り（認証レベル）を管理しつつ、詳細な権限フラグはDynamoDBの`Roles`テーブルで管理する。API呼び出し時、Lambda側で対象ユーザーのロールに紐づく権限フラグを参照し、処理可否を判定する
- 誤操作防止のため、最後の1名の管理者権限は削除できない等のガード処理を設ける

#### 5.1.4 職員カテゴリ（雇用形態区分）
- ロール（権限）とは別軸の属性として、**職員カテゴリ**を用意する
- 初期カテゴリ：正職員／契約職員／パート・アルバイト／外部職員
- カテゴリは固定せず、**管理者画面から追加・編集・削除が可能**
- 職員カテゴリは、グループチャットのメンバー一括選択（5.2.1参照）と、掲示板の閲覧権限設定（5.3.3参照）に利用する
- **実装方針**：DynamoDBの`StaffCategories`テーブルでカテゴリ一覧を管理し、`Users`テーブルの`staffCategoryId`で各ユーザーに紐づける

### 5.2 チャット機能

#### 5.2.1 基本機能
- 1対1チャット
- グループチャット（クラス単位／学年単位／全体連絡用など自由に作成可）
  - グループ作成時、**職員カテゴリを指定してメンバーを一括選択**できる補助機能を提供（例：「パート・アルバイト」を一括追加 等）
- 既読／未読管理
- 画像・ファイル添付（Amazon S3）
- メッセージ検索

#### 5.2.2 予約送信機能
- メッセージ作成時に送信日時を指定し、指定時刻に自動送信
- **実装方針**
  1. メッセージを `status: scheduled` としてDynamoDBに保存（`scheduledAt` 属性を保持）
  2. Amazon EventBridge Schedulerに指定時刻のワンタイムスケジュールを登録
  3. 指定時刻にLambdaが起動し、`status: sent` へ更新、AppSync経由でチャットルームへ配信、プッシュ通知処理を実行
  - 予約中メッセージの取消・編集機能もあわせて提供（送信済みは編集不可）
  - タイムゾーンは園の所在地（Asia/Tokyo）を基準に統一

#### 5.2.3 緊急通知（通知オフを無視する）機能
- 管理者等の権限を持つユーザーが送信時に「緊急連絡として送信」を選択すると、通知オフのユーザーにも強制的にプッシュ通知が届く
- **実装方針**：メッセージに `forceNotify: true` フラグを付与し、プッシュ通知送信Lambda内で `forceNotify` がtrueの場合は受信者の `notificationStatus` を無視して送信する
- 濫用防止のため、フラグの利用は管理者ロールなど限定された権限のユーザーのみに許可する
- **音声通話にはこの緊急通知フラグの仕組みを適用しない**（5.2.4参照）

#### 5.2.4 音声通話（1対1）
- Amazon Chime SDKを利用した**1対1音声通話**（映像通話・グループ通話は今回のスコープ外）
- チャット詳細画面（1対1トークのみ）から発信可能
- 着信通知はプッシュ通知＋アプリ内リアルタイム通知（AppSync）で実現
- **通知オフのユーザーには着信通知は届かない**（例外なし。「つながらない権利」を最優先する設計）
- 通話音声データそのものは録音・保存しない方針（メタデータのみ記録）
- 通話ログ（発着信時刻・通話時間・応答状況）を `CallLogs` テーブルに保存
- iOS/AndroidネイティブのCallKit／ConnectionService連携（バックグラウンド時の着信確実性向上）は次フェーズで検討

### 5.3 掲示板

#### 5.3.1 カテゴリー別表示
- 投稿時にカテゴリー（例：お知らせ／行事／緊急連絡など、園側で設定可能）を選択
- 一覧画面はカテゴリータブ／フィルターで絞り込み表示可能

#### 5.3.2 ファイル添付
- 画像・PDF・Office文書等の添付に対応
- Amazon S3に保存し、署名付きURL（有効期限付き）で配信
- ファイルサイズ・形式の制限を設定（例：1ファイルあたり最大10MB、拡張子制限 等、運用に合わせて調整）

#### 5.3.3 閲覧権限（職員カテゴリ別）
- 投稿時に、閲覧可能な職員カテゴリ（正職員／契約職員／パート・アルバイト／外部職員 等）を複数選択で指定可能
- 未指定の場合は全職員に公開
- **実装方針**：`BulletinPosts`テーブルに`visibleCategoryIds`（配列）を保持し、一覧取得APIで閲覧者の`staffCategoryId`と照合してフィルタリングする

#### 5.3.4 掲示板更新時の通知
- 新規投稿の公開時、および既存投稿の更新時にプッシュ通知を送信する
- 通知対象は、当該投稿の閲覧権限を持つ職員カテゴリに属し、かつ通知オンのユーザーに限定する
- **実装方針**：`BulletinPosts`の作成・更新をトリガーにLambdaを起動し、`visibleCategoryIds`に該当する`Users`のうち`notificationStatus`がONのユーザーへPinpoint/SNS経由でプッシュ通知を送信する

---

### 5.4 カレンダービュー
- Googleカレンダーの予定を**閲覧専用**で表示（アプリからの編集は不可）
- OAuth2.0によるGoogleアカウント連携（園の共有カレンダーを参照する想定）
- Lambdaが定期的にGoogle Calendar APIから予定を取得し、DynamoDB（`ScheduleCache`）にキャッシュして表示速度を確保
- 月表示／週表示の切り替えに対応

---

### 5.5 外部リンク集（ブックマーク）
- 申請機能の代替として、Googleフォーム（休暇申請・備品購入申請等）や、その他組織ごとに使用するWebサービスへのリンクを一覧化する機能
- 管理者がタイトル・URL・カテゴリー（任意）を登録し、一般職員は一覧から選択してタップするだけで該当サイトを開ける
- リンクはOS標準ブラウザ、またはアプリ内ブラウザ（WebView）で開く方式を想定（初期はOS標準ブラウザ起動が最もシンプルで開発コストも小さい）
- カテゴリー分け・並び替えに対応し、掲示板と同様の一覧UIコンポーネントを流用してコストを抑える
- **実装方針**：シンプルなCRUD機能のため、既存のAPI Gateway + Lambda + DynamoDBの構成に`OrgLinks`テーブルを追加するのみで実現可能。新たなAWSサービスの追加は不要で、開発・運用コストへの影響は軽微。

## 6. 非機能要件

| 分類 | 要件 |
|---|---|
| セキュリティ | 通信の全面TLS化、保存データの暗号化（KMS）、個人情報保護法に準拠した取り扱い |
| 可用性 | マルチAZ構成、目標稼働率 99.9% |
| 性能 | チャットメッセージの配信遅延を数秒以内に抑制、予約送信は指定時刻±1分程度の精度を目標 |
| 通話品質 | Chime SDKのWebRTC基盤に準拠、回線状況による品質劣化時のリトライ・再接続を実装 |
| プライバシー | 通話音声は保存しない（メタデータのみ記録）、通知オフ設定は例外なく尊重する |
| 拡張性 | サーバーレス構成による自動スケーリング |
| バックアップ | DynamoDBのポイントインタイムリカバリ、定期バックアップ取得 |
| 監査 | 操作ログ・アクセスログの保存（CloudTrail）、緊急通知の送信履歴の記録 |

## 8. データ設計（主要テーブル例）

| テーブル名 | 主な属性 |
|---|---|
| Users | userId、氏名、roleId、staffCategoryId、notificationStatus（ON/OFF）、所属クラス 等 |
| Roles | roleId、ロール名、permissions（権限フラグのマップ：ユーザー管理／緊急通知送信／掲示板カテゴリ管理／リンク集管理 等） |

| CallLogs | callId、callerId、calleeId、startTime、endTime、duration、status（completed/missed/declined） |
| OrgLinks | linkId、タイトル、URL、カテゴリー（任意）、並び順、登録者、更新日時 |

## 9. 予算感（AWS利用料 概算）

### 9.1 前提条件
- 想定利用者数：35人
- チャット・掲示板トラフィック：1人あたり1日3投稿程度
- 音声通話：1日あたり合計1時間程度（1対1通話）
- リージョン：東京（ap-northeast-1）、為替レート 1ドル＝150円換算

### 9.2 月額費用の目安

| サービス | 月額目安（USD） | 備考 |
|---|---|---|
| Cognito（認証） | $0 | 無料枠が10,000MAUまであり、35人なら完全に無料 |
| Lambda | $0 | 無料枠（月100万リクエスト）内に収まる規模 |
| API Gateway | 〜$1 | 月間リクエスト数が少なく低額 |
| AppSync（チャット） | $1〜3 | GraphQL呼び出し・接続維持分 |
| DynamoDB | $1〜3 | オンデマンド課金、データ量がごく僅か |
| S3（添付ファイル） | 〜$1 | ストレージ量が少ないため僅少 |
| CloudFront | 〜$1 | データ転送量が少ないため僅少 |
| Pinpoint/SNS（プッシュ通知） | 〜$1 | 通知件数が少ないため僅少 |
| EventBridge Scheduler（予約送信） | ほぼ$0 | 呼び出し回数が少なく実質無料 |
| Chime SDK（音声通話） | $6〜8 | 1日60分×2人分×30日≒3,600分/月 × $0.0017/分・人 |
| AWS WAF（任意） | $5〜10 | Web ACL基本料＋ルール数課金。園内限定利用なら初期は省略も選択肢 |
| **合計目安** | **$15〜30/月** | 日本円で約2,300〜4,500円/月 |

### 9.3 補足
- この規模では、使用量そのものより「固定費的なサービス」（WAFなど）が総額を左右しやすい。職員限定のクローズドなアプリであれば、初期はCognito認証のみで運用し、WAFは後から追加する選択肢もある。
- Apple Developer Program（年間$99）、Google Play Console（初回$25）はAWS利用料とは別途必要。
- 実際の請求額は為替・トラフィックの増減で変動するため、あくまで目安である。
- ユーザー数・投稿数・通話時間が増加しても、35人〜100人程度の規模であれば、月額数十ドル程度の範囲に収まる見込み。
- 外部リンク集（ブックマーク）機能は既存のDB/API構成へのテーブル追加のみで実現するため、追加コストはほぼ発生せず、上記合計に含めて考えて差し支えない。

## 12. まとめ

On-Connectは、「大規模チーム向けサービスの過剰さ」と「小〜中チーム向けサービスの物足りなさ」の間を埋める、幼稚園・保育園・学校特化型のコミュニケーションアプリである。私用端末が業務連絡のメイン端末になりがちな現場の実情を踏まえ、通知ON/OFFという仕組みを中核に据え、音声通話を含むすべての通知が「つながらない権利」を例外なく尊重する設計とした。申請機能は自前実装せずGoogleフォーム等の外部サービスへのリンクで代替し、ユーザー管理・チャット・掲示板・カレンダービュー・1対1音声通話・外部リンク集の6つの中核機能に絞り込むことで、35人規模であれば月額$15〜30程度のAWS利用料で運用可能な、身の丈に合ったシステムを目指す。また、ロール権限や職員カテゴリを管理者画面から柔軟にカスタマイズできる設計とすることで、園ごとの組織構成や運用ルールの違いにも対応できるようにする。
